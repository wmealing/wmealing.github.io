Summary:

The counter in Concrete 002 runs only in the browser. The + button does not send data to the server.

This article adds a new function to that counter. The click still updates the screen at once. But the button also sends the new count to the server. The server writes the count to the log.

The first method did not work. The code was correct. The build had no errors. The code ran with no errors. But the code sent no data.

This article shows the correct method. It also shows the error and the fix for the error. It also corrects a wrong statement in Concrete 005.

Send Data To The Server

action/3 runs in the browser. The compiler makes JavaScript code from this function.

command/3 is different. concrete_command_handler runs this function on the server. The browser sends a POST request to /concrete/command. This request starts the function.

Use ?js:call to start Client.dispatchCommand from an action. This method is similar to the concrete-command button attribute. But this method can send real data. The button attribute can only send an empty map. 

-include_lib("concrete/include/concrete_js.hrl").

%% This code runs in the browser.
%% The click updates the count at once.
%% The call to dispatchCommand does not stop the update.
action(increment, _Params, #{state := #{count := N} = S} = C) ->
    NewCount = N + 1,
    ?js:call(<<"Client">>, dispatchCommand,
             [<<"report_count">>, #{count => NewCount}]),
    C#{state => S#{count := NewCount}}.

%% This code runs on the server.
%% concrete_command_handler starts this function.
%% Params is a normal map. It is not in wire format.
command(report_count, Params, Server) ->
    error_logger:info_msg("counter is now: ~p~n", [Params]),
    Server.

Click the + button. command/3 must run on the server. Params must equal #{<<"count">> => 1}.

No Error, But No Result

The build was successful. The page loaded correctly. The button worked. The count went up on the screen.

No message appeared in the server log. No error appeared in the browser console.

I checked each step in order. The click handler started correctly. The compiled function ran correctly. Erlang["concrete_js:call/3"] ran with the correct arguments.

I added a test function to the live page. This function replaced Erlang["concrete_js:call/3"] with a new function. The new function recorded its arguments. Then it called the original function. 

const oc = Erlang["concrete_js:call/3"];
Erlang["concrete_js:call/3"] = function (...a) {
  console.log("called with", a);
  return oc.apply(this, a);
};

The test showed that the function started correctly. It received the correct receiver, method, and arguments. But the function still returned undefined. The function did not call fetch.

The problem was inside the function. The problem was not at the call location.

I checked the function code with Erlang["concrete_js:call/3"].toString(). The code did not match the real function in runtime.js. The code matched a different function. Interpreter.defineErlangFunction creates this different function for compiled modules: 

(...args) => {
  const result = impl(args);
  if (result && typeof result.next === "function") {
    return Interpreter.runEphemeral(result);
  }
  return result;
}

A compiled version of concrete_js:call/3 existed. This version used the same name as the real function. The build tool replaced the real function with the compiled version. The compiled version has one simple body: call(_Receiver, _Method, _Args) -> undefined.. This is why the function returned undefined. This is why the function raised no error.

The Cause Of The Error

Concrete 005 made an incorrect statement. It said the call graph treats concrete_js like dom. It said the call graph finds no code for concrete_js. This statement is wrong.

The debug_info compiler flag causes this error. This flag is a default setting in rebar3.

dom has no source file. The build tool cannot find any code for dom.

concrete_js is different. Each function in concrete_js has real code. This code lets an action run correctly on the server, not only in the browser. With the debug_info flag on, this code is available to the build tool.

Without a fix, rebar_compiler_concrete:populate_mfa/2 reads this code. The call graph then treats concrete_js:call/3 as normal project code. concrete_encoder compiles the real function body. The build tool saves this new function under the name Erlang["concrete_js:call/3"]. This action replaces the correct native function. Every ?js:call in the bundle still compiles. Every ?js:call still runs. But no ?js:call sends any data.

The Fix

concrete_js.erl now has a new module attribute: 

-concrete([{bif_module, true}]).

concrete_beam_reader:extract_ir/1 checks for this attribute. If the module has this attribute, the function stops. The function returns the same result as it does for dom. 

is_bif_module(Forms) ->
    lists:any(
        fun({attribute, _, concrete, Opts}) -> proplists:get_value(bif_module, Opts) =:= true;
           (_) -> false
        end,
        Forms
    ).

This fix solves the problem for concrete_js. It does not solve the problem for a new module that forgets this attribute. runtime.js has a second check for this reason.

defineErlangFunction now checks a list of native BIF names. The system creates this list before it runs any compiled code. If new code tries to use an existing name, the system stops. The system shows an error message: 

const nativeBifKeys = new Set(Object.keys(Erlang));

defineErlangFunction(moduleName, funcName, arity, clauses) {
  const fullKey = `${moduleName}:${funcName}/${arity}`;
  if (nativeBifKeys.has(fullKey)) {
    throw new Error(
      `Refusing to overwrite native BIF Erlang["${fullKey}"] with a compiled definition. ` +
      `${moduleName} should be tagged -concrete([{bif_module, true}]) so ` +
      `concrete_beam_reader:extract_ir/1 never traces into it.`
    );
  }
  ...
}

If a developer forgets the attribute, the build shows an error at once. The bundle will not fail without a warning.

The Rules For command/3

command/3 is also a compile target. The build tool treats command/3 the same as action/3. A browser can call command/3 directly, through an HTTP request or through a WebSocket connection.

The build tool tries to translate all the code inside command/3. This rule applies even when the function only runs on the server. Because of this rule, command/3 cannot use every Erlang function.

io:format/2 and logger:info/1,2 do not work here. These functions load too much code from the standard library. The build tool cannot translate this code.

error_logger:info_msg/2 works correctly. This function sends output to the shell or to the log file. The example in this article uses this function for that reason.

Test The Fix

test/beam_reader_SUITE.erl has two tests: bif_module_is_refused and concrete_js_is_refused. These tests confirm that extract_ir/1 stops at the new attribute.

test/rebar_compiler_concrete_SUITE.erl has a test named populate_plt_never_traces_concrete_js. This test runs the real build process against a test page. The action/3 function in that page calls concrete_js:call/2. The test confirms that the build tool saves no concrete_js functions.

test/js_exec_SUITE.erl has a test named defining_over_native_bif_throws. This test runs runtime.js with Node.js. It confirms that the new check works correctly.

What Comes Next

This article showed one method. A client action can send data to the server.

The concrete-command button attribute is a simpler method. But this attribute always sends an empty map. There is no way to add real data to this attribute yet.

The WebSocket connection is a different method. concrete_ws_handler can run action and command functions on the server through one connection. This method still needs more documentation.
